## 2. 관람객 정의 (이 문서의 모든 판단 기준)

- 창업 캠프를 지나가는 **일반인**. 학생·지역 주민·타 팀 참가자.
- **응애가 뭔지 모른다.** 벌통 사진을 봐도 그냥 벌떼로 보인다.
- 부스 앞 체류 시간 **30초~1분**.
- 목표: "아, 이런 앱이구나" + 좋은 인상. 그 이상 욕심내지 않는다.

> ⚠️ 심사위원·투자자 대응은 **이 부스의 목적이 아니다.** 사업계획서/심사 Q&A 논리를
> 이 앱에 넣지 말 것. (2026-08-30 사용자 확인)

### 이 기준으로 **뺀** 것

| 뺀 기능 | 이유 |

### [5-a] 기록 보기 — "기록"의 정의

결과 화면 우하단 `[기록 보기]`로만 들어가는 곁가지 화면. 메인 흐름이 아니다.

- **미리 심어둔 과거 4주치 4점**(고정값) + **이번 세션에 관람객이 진단한 건**이 뒤에 얹힌다.
- 1점짜리 밋밋한 그래프를 피하기 위한 장치다. 관람객이 위험 사진을 고르면 마지막 점이 확 치솟는다.
- **세션 초기화 시 관람객이 진단한 점만 지워지고, 심어둔 4점은 매번 복원된다.**
- 심어둔 4점은 실제 데이터가 아니므로 화면에 **"예시 기록"** 이라고 작게 표기한다.

### 설계 의도

- **[3]이 이 부스의 유일한 참여 지점이다.** 관람객이 직접 판단하고 → AI가 답을 준다.
  사업계획서 Q5의 *"우리가 없애는 건 내검이 아니라 판독"* 을 관람객이 몸으로 겪는 구간.
  줄이 길면 `[바로 결과 보기]`로 건너뛴다.
- 정상 사진을 골라 "건강함"을 맞히면 *"정확합니다! 이 벌통은 건강합니다"* 로 기분 좋게 끝낸다.
  틀렸을 때 톤은 **위로**("전문가도 어렵습니다"), 절대 조롱하지 않는다.

## 5. 결과 수치는 어떻게 나오는가

모델 추론을 돌리지 않는다. **정답 라벨 → 프로덕션 코드가 계산**한다.

```
AI Hub 라벨 JSON (category_id 0~6, COCO bbox)
   │ training/data/aihub_to_yolo.py : CLASS_MAPPING   (7-class → 3-class)
   ▼
class_counts {0: normal, 1: varroa, 2: other}
   │ app/services/risk.py : compute_risk()            ← 프로덕션 코드 그대로 호출
   ▼
risk_score · tier · recommendations[]  →  assets/cases.json
```

**risk·티어·처방 문구를 손으로 적지 않는다.** `risk.yaml`이 바뀌면 스크립트만 다시 돌리면
되고, 문구가 실제 앱과 영원히 어긋나지 않는다.

### 검증 완료 (2026-08-30)

기존 `demo-assets/` 6장으로 대조한 결과 — 라벨 기준 수치가 **실제 앱 E2E 값과 티어 전부 일치**:

처방 개수(5/5/4/4/3/3)까지 동일했다. 부스에서 *"실제 모델도 거의 같은 값을 냅니다"* 라고

## 6. ⚠️ 검증에서 드러난 제약 — 응애는 눈에 보이지 않는다

**설계를 바꾼 가장 중요한 발견이다.** 응애 라벨 보유 95장을 전수 측정하고 상위 후보를
직접 눈으로 확인한 결과:

- 응애 크롭 **밝기 최대 59/255**. 대부분 30~50. 전부 어둡고 모션 블러가 있다.
- 라벨 박스가 **"응애"가 아니라 "감염된 벌 영역"**(`AIHUB_71667.md` §6, Q3=B)이라
  면적 중앙값이 화면의 24~40%이고, **벌 여러 마리를 포함**한다.
- 가장 선명한 크롭을 밝기 2.2배 보정해도 붉은 타원이 *"있는 것 같다"* 수준이다.

### 이 제약이 무너뜨린 것

| 당초 설계 | 판정 |
|---|---|
| [5] 감염 벌 자동 줌인 (클라이맥스) | ❌ **철회.** 확대하면 관람객이 "뭐가 다른데요?"라고 되묻고 신뢰가 깎인다 |
| [3] "응애를 직접 찾아보세요" | ❌ 결과를 봐도 여전히 안 보여 카타르시스가 없다 → **"이 벌통, 건강해 보이나요?"** 로 변경 |
| [5] 정상 벌 박스까지 전부 그리기 | ❌ **철회.** 박스 6~14개가 서로 겹치고 화면 밖으로 잘려 난장판이 된다 → **응애 박스만** |
| [1] 응애 소개 사진을 데이터셋에서 조달 | ✅ **가능했다.** `유충_응애/046` C_ 촬영본에서 응애 2마리가 선명하다 — §4 |

### 남은 연출

**응애 박스 1개**를 그리는 것까지다. 실측 결과 응애 박스만 남기면 벌 한 마리를 정확히
감싸는 그림이 나온다(#1·#2·#3 육안 확인 완료). **확대는 하지 않는다.**

### 사진 선정 기준 (이 제약에서 도출됨 — 사진 교체 시 반드시 재적용)

1. 응애 박스가 **정확히 1개** (2개면 겹친다)
2. 박스가 이미지 경계에서 **20px 이상 여유** (잘리면 안 된다)
3. 박스 면적 **8~32%**
4. 원본 밝기 **≥ 48/255**
5. 기타질병 인스턴스 **0개** (다른 질병 처방이 섞이면 관람객이 혼란스럽다)

330장 중 이 5개를 모두 통과한 것은 **24장**이고, 그중 danger는 **3장뿐**이다.

### 외부 패키지를 쓰지 않는 이유

네트워크·카메라·보안저장소를 쓰지 않으므로 `dio`/`camera`/`flutter_secure_storage`가
필요 없다. 게이지·그래프는 `CustomPainter`, QR은 정적 PNG로 처리한다.
→ **`flutter build web`이 깨질 지점이 사라진다.** "네이티브 + 웹 백업"을 사실상 공짜로
만드는 결정이다.

### 상태 관리

## 8. 데이터 생성 파이프라인 (1회성)

`apps/ai/training/data/make_booth_cases.py` (신규)

1. 4장의 라벨 JSON 파싱
2. `CLASS_MAPPING` 적용 → `class_counts`
3. `compute_risk()` 호출 → risk / tier / recommendations
4. bbox를 `[x, y, w, h]` 픽셀 그대로 + 클래스(varroa / normal) 부착
5. 원본 JPG를 밝기·대비 보정 + 긴 변 1600px 리사이즈 → `apps/booth/assets/photos/`
6. `cases.json` 출력

```jsonc
{
  "cases": [{
    "id": "danger-100",
    "photo": "photos/01_danger_100.jpg",
    "imageWidth": 1920, "imageHeight": 1080,
    "riskScore": 100, "tier": "danger",
    "infestationRate": 28.6, "beeTotal": 7, "varroaCount": 2,
    "recommendations": ["응애 감염률이 위험 범위(10% 이상)입니다. 즉시 처치가 필요합니다.", "..."],
    "boxes": [{"x": 224, "y": 413, "w": 814, "h": 664, "cls": "varroa"}, ...]
  }]
}
```

## 9. 아이패드 · 키오스크

- **가로 고정** — `ios/Runner/Info.plist`에서 세로 제거 + `SystemChrome.setPreferredOrientations`.
  현재 `apps/mobile`은 4방향이 전부 열려 있으므로 새 앱에서 반드시 잠근다.
- 기준 해상도 **1366×1024 논리 픽셀**. 결과 화면은 좌 사진 60% / 우 게이지+처방 40% 2단.
- 본문 **22pt 이상**, 위험도 숫자 **96pt**. 서서 보는 화면이다.
- 숨은 운영자 제스처: **좌상단 5회 탭 → 강제 초기화**.
- 운영 절차(런북에 기재): **안내 접근(Guided Access) 켜기 · 자동 잠금 끄기 ·
  저전력 모드 끄기 · 밝기 최대**.
