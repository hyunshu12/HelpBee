## 0. 앱이 하는 일 (30초 요약)

이 앱은 **인터넷도, 서버도 필요 없다.** 사진 4장과 그 진단 결과가 앱 안에 전부 미리 들어있고,
관람객이 사진을 고르면 그 사진에 맞는 결과를 보여줄 뿐이다. 실시간으로 AI가 도는 게 아니다.

화면은 이 순서로 흐른다:

```
어트랙트(대기 화면, 자동 반복)
  → 터치 → 인트로("응애가 뭐죠?", 사실 3줄이 차례로 뜨고 **25초 후** 자동 진행 / 탭하면 즉시)
    → 사진 선택 (4장 중 1장 고르기)
      → 추측("건강해 보이나요?" 3버튼)
        → 분석 중 (1.5초, 연출용)
          → 결과 (위험도 + 처방)
            → [기록 보기] 또는 [다른 사진 해보기] 또는 [QR 받기]
              → 마무리 (QR 코드, 15초 후 자동으로 처음 화면)
```

**아무 화면에서나 60초 동안 아무도 안 건드리면 자동으로 대기 화면(어트랙트)으로 돌아간다.**
관람객이 중간에 그냥 가버려도 다음 사람을 위해 스스로 정리되는 구조다. 어트랙트 화면 자체는
방치해도 초기화되지 않고 계속 반복 재생만 한다(초기 상태이므로).

## 1. 부스 전날 준비

전부 ✅ 여야 다음 날 아침에 켜기만 하면 된다.

### 1-1. 아이패드 설정 4가지

**설정 앱**에서:

1. **자동 잠금 끔** — 설정 > 화면 자동 잠금 > **안 함**
2. **저전력 모드 끔** — 설정 > 배터리 > 저전력 모드 **꺼짐**
3. **화면 밝기 최대** — 조절 센터(우측 상단에서 아래로 스와이프)에서 밝기 슬라이더를 끝까지
4. **손쉬운 사용 > 안내 접근(Guided Access) 켜기** (동작 확인은 §1-3, 실제 사용은 §2)
   - 설정 > 손쉬운 사용 > 안내 접근 > **켜짐**으로
   - **암호 설정** — 임의 숫자 4자리를 정한다.
   - **암호를 부스 현장에 물리적으로 적어 비치한다** — 거치대에 테이프로 붙이거나 운영자
     수첩에 적어 항상 몸에 지닌다. 기억에만 의존하지 않는다.
   - **암호를 잊어버렸을 때 복구 방법** — 사이드(전원) 버튼 3번으로는 암호 없이 못 끈다.
     그럴 땐 기기를 **강제 재시작**한다: 상단(전원) 버튼과 볼륨 버튼(위 또는 아래 아무거나)을
     **동시에 길게 눌러 Apple 로고가 뜰 때까지** 기다린다. 강제 재시작하면 안내 접근이
     자동으로 해제된다(단, 앱은 강제 종료되므로 §3-②의 4~5번처럼 다시 켜야 한다).
   - "잠금 시작 시간 종료" 옵션은 **꺼둔다** (하루 종일 켜져 있어야 하니까).

### 1-2. 앱 설치 확인

홈 화면에 이 앱 아이콘("Helpbee Booth")이 있는지, 눌러서 **대기 화면(사진+위험도 게이지)이
뜨는지** 확인한다. 안 뜨면 개발자(팀 내 기술 담당자)에게 먼저 연락 — 이 런북은 설치 자체를
다루지 않는다.

### 1-3. 안내 접근 동작 확인 (미리 한 번 눌러볼 것)

1. 앱을 연다.
2. 사이드 버튼(전원 버튼)을 **빠르게 3번** 누른다.
3. 화면 아래 "안내 접근 시작"이 뜨면 손가락으로 원을 그려 켜고 싶은 제한 영역을 확인한 뒤
   우측 상단 **시작**을 누른다.
4. 이 상태에서 홈 버튼 제스처(화면 아래에서 위로 쓸어올리기)를 시도해본다 — **아무 반응이
   없어야 정상**이다 (이게 안내 접근이 하는 일).
5. 끄려면 사이드 버튼을 다시 3번 누르고, 암호를 입력하고, **종료**를 누른다.

이 절차가 낯설면 당일 아침에 급하게 하지 말고 **오늘 미리 한 번 해볼 것.**

### 1-4. 웹 백업 캐시 채우기 + 홈 화면 추가

> ⚠️ **2026-08-30 기준, 이 항목은 아직 준비되지 않았다.** 웹 백업(사파리로 여는 버전)은
> 별도 작업(Task 9)에서 배포될 예정이고, 이 문서를 쓰는 시점엔 배포된 URL이 없다.
> **부스 전날까지 팀 내 기술 담당자에게 웹 백업 URL을 받아 이 섹션의 빈칸을 채워야 한다.**
> URL이 없다면 §3의 "③ 아이패드가 안 되면" 대응이 불가능하다는 뜻이니, 최소한 예비 아이패드나
> 예비 기기를 하나 더 준비하는 것으로 대신한다.

URL을 받으면:

1. 사파리로 `(웹 백업 URL — 여기에 채울 것)` 을 연다.
2. 화면이 앱과 똑같이(가로로, 사진+게이지) 뜨는지 확인한다. 처음 열 때 약 13MB를 받으므로
   와이파이가 있는 곳에서 미리 열어둔다 — **부스장은 와이파이가 불안정할 수 있다.**
3. 공유 버튼(□ 위 화살표) > **홈 화면에 추가**. 이러면 아이콘이 생기고, 다음부터는 인터넷
   없이도 그 아이콘으로 바로 열린다(첫 로딩분은 이미 캐시됨).
4. 앱과 똑같이 사진 4장을 한 번씩 눌러보고 정상 동작하는지 확인한다.

### 1-5. QR 스캔 확인

마무리 화면의 QR을 **다른 사람 폰**으로 스캔해서 `https://www.mrmr.kr/` 로 이동하는지 확인한다
(팀 홈페이지). 스캔이 안 되거나 다른 곳으로 가면 기술 담당자에게 알린다.

### 1-6. 충전

**100%까지 충전**하고, 가능하면 부스 당일에도 **충전기를 꽂아둔 채로 운영**한다(§2 참고).
충전 케이블·어댑터를 부스 짐에 챙긴다.

## 2. 당일 개장 절차

1. 아이패드를 거치대에 **가로**로 놓는다. (세로로 두면 안 돌아간다 — 정상이다. §"이상 시
   대처" 아님, 원래 그렇게 만들었다.)
2. 앱을 실행한다. 대기 화면(사진과 빨간/초록 박스, 오른쪽에 위험도 숫자)이 자동으로 반복
   재생되는지 확인한다.
3. 가능하면 **충전기를 꽂은 채로** 거치대에 고정한다 — 하루 종일 화면을 최대 밝기로 켜두므로
   배터리 소모가 크다.
4. §1-3 순서대로 **안내 접근을 켠다.** 관람객이 앱을 벗어나거나 아이패드를 만지다가 다른 앱으로
   나가는 걸 막기 위함이다.
5. 화면을 몇 번 터치해서(대기 화면 → 인트로 → 사진 선택 정도) 정상적으로 넘어가는지 눈으로
   확인한 뒤, 좌측 상단 모서리를 **빠르게 5번** 눌러 대기 화면으로 되돌려 놓는다(§3-① 참고).
   이제 개장 준비 완료.

## 3. 이상 시 대처

### ① 화면이 멈췄다 / 관람객이 다음 사람을 위해 화면을 리셋해줘야 한다

**화면 좌측 상단 모서리를 빠르게 5번 두드린다.** (아이콘도 표시도 없는 투명한 영역이라
관람객 눈에는 안 띈다 — 운영자만 아는 제스처다.) 3초 안에 5번을 채워야 발동한다. 성공하면
바로 대기 화면으로 돌아간다.

- 4번만 누르고 3초 넘게 쉬었다가 다시 누르면 **처음부터 다시 5번**을 채워야 한다(느리게
  누르면 안 먹힌다는 뜻 — 정상 동작이다. 무한정 천천히 눌러도 안 되니 빠르게 연타할 것).

### ② 앱이 죽었다 / 얼어서 아무 반응도 없다

1. 안내 접근을 끈다 — 사이드 버튼 3번 → 암호 입력 → **종료**.
2. 홈 버튼 제스처(아래에서 위로 쓸어올리기, 잠깐 멈췄다 놓기)로 앱 스위처를 연다.
3. 이 앱 카드를 위로 쓸어올려서 강제 종료한다.
4. 홈 화면에서 앱 아이콘을 다시 눌러 실행한다.
5. 대기 화면이 뜨는 걸 확인하고 §1-3 순서로 **안내 접근을 다시 켠다.**

### ③ 아이패드 자체가 안 된다 (전원이 안 켜지거나 화면이 완전히 나갔다)

§1-4에서 준비해둔 **웹 백업**을 쓴다. 예비 폰이나 예비 태블릿의 사파리에서 홈 화면에 추가해둔
아이콘을 눌러 그대로 진행한다. 인터넷이 없어도 첫 로딩을 미리 해뒀다면 동작한다.

> 웹 백업 URL이 아직 없다면(§1-4 참고) 이 대응 자체가 불가능하다 — 부스 전날까지 반드시
> 확보할 것.

## 4. 관람객 응대 — 하지 말아야 할 말

이 앱은 **미리 골라둔 사진 4장의 결과를 보여주는 시연**이지, 그 자리에서 AI가 실시간으로
계산하는 게 아니다. 그리고 실제 모델 정확도는 사진 종류에 따라 편차가 크다(§5 참고). 그래서:

**❌ 하지 말 것**
- "정확도 92%입니다" 류의 숫자 주장
- "AI가 정확히 잡아냅니다"
- 성충(다 자란 벌) 사진에서 응애를 놓치는 걸 두고 "데이터가 부족해서 그렇다" 는 식의 단정
  — **이건 원인이 우리 쪽 라벨 파싱 버그일 가능성이 있고(§5), 아직 재학습 전이라 확정된
  설명이 아니다.** 모르면 "확인 중입니다" 정도로 답한다.

**✅ 대신 이렇게 말할 것**
- "사진 한 장 찍으면 이런 흐름으로 결과가 나오는 방식이에요"
- "지금 보여드리는 건 미리 준비한 사진 4장이고, 실제 서비스는 사진을 그 자리에서 분석합니다"
- 정확도를 물어보면: "아직 검증 중인 초기 버전이라 정확한 수치를 말씀드리긴 이릅니다"

근거 문서: `plans/2026-08-12_시연-영상-계획.md` §5 (330장 전수 검사 결과 — 성충 응애
미탐률 82%, 오탐 18~24%), `docs/03-refactoring/2026-08-30-aihub-bbox-format-misparse.md`
(학습 데이터 라벨을 잘못 해석한 버그가 발견됐고, 저 미탐률의 원인일 수 있다는 내용 — 아직
수정 전).

## 5. 사진 출처

앱에 들어있는 벌 사진은 **AI Hub 71667 (꿀벌 질병 진단 이미지 데이터)** 에서 가져온 것이다.
이 데이터셋은 **재배포가 금지**되어 있다(내국인만 신청 가능한 라이선스).

관람객이 "이 사진 좀 찍어가도 되나요?" / "화면 촬영해서 SNS에 올려도 되나요?" 라고 물으면:

> "죄송하지만 이 사진들은 저작권 제약이 있어서 개별 공유는 어려워요. 대신 QR로 저희 팀
> 홈페이지에서 더 보실 수 있어요."

정중히 거절하고 QR(마무리 화면)로 유도한다. 앱 화면 전체를 부스 홍보용으로 촬영하는 것 자체는
문제없다(사진 개별 클로즈업 공유·전달만 피하면 된다).

## 7. 에이전트가 검증하지 못한 것

이 런북과 앱 레이아웃은 2026-08-30에 **iOS 시뮬레이터**(iPad Air 13-inch, macOS 위에서
가상으로 구동)로만 확인했다. 실물 아이패드가 이 작업 환경에 없었고, Apple 개발자 계정 준비
여부도 불확실해 **Step 4(실물 설치)와 Step 5(실물 체크리스트)는 아예 시도하지 않았다.**
다음은 그중에서도 **시뮬레이터로는 원천적으로 확인이 안 되는 것들**이다 — 부스 전 리허설을
하는 사람이 반드시 직접 손으로 눌러서 확인해야 한다.

- **모든 물리 탭 경로** — 시뮬레이터에 손가락 터치를 흉내 낼 방법이 없어(이전 세션들도 동일한
  한계를 기록함 — 시뮬레이터 창이 포커스를 받지 못함), 8개 화면 전부 **코드에서 초기 화면을
  임시로 바꿔치기**해서 스크린샷만 확인했다. 실제로 손가락으로 사진을 누르고, 버튼을 누르고,
  다음 화면으로 넘어가는 그 자체(제스처 인식, 터치 반응 속도, 오터치 여부)는 **한 번도 실기로
  확인되지 않았다.**
- **화면별 60초 무동작 복귀** — 코드상 타이머 로직은 자동화 테스트로 통과했지만, 실물에서
  "정말 만지지 않고 60초를 기다렸을 때" 6개 화면(인트로/사진선택/추측/결과/기록보기, 그리고
  어트랙트에서는 리셋되지 않아야 함) 전부가 그대로 동작하는지는 실측하지 않았다.
- **QR 스캔** — 실제 폰 카메라로 화면의 QR을 찍어 `https://www.mrmr.kr/` 로 이동하는지
  확인하지 못했다(§1-5는 부스 전날 사람이 직접 할 일로 남겨둠).
- **운영자 5연타 제스처의 실제 히트 영역** — 코드상 좌측 상단 60×60(pt) 투명 영역이 맞는지
  로직은 확인했지만, **실기에서 손가락으로 그 자리를 정확히 짚을 수 있는지, 화면 좌표계가
  실기와 시뮬레이터에서 동일한지는 확인하지 못했다.** 크기가 애매하면 관람객이 우연히 5번
  건드릴 가능성, 또는 운영자가 자리를 못 찾을 가능성 둘 다 있다.
- **3시간 연속 구동** — 배터리 소모율, 발열, 장시간 최대 밝기 구동 시 안정성은 전혀 테스트
  되지 않았다. 부스 전날 최소 1회는 실제로 몇 시간 켜둔 채 방치해볼 것을 권한다.
- **기록 그래프의 티어 색·점 크기** — 이번 세션에서 시뮬레이터로 danger 케이스를 기록한 뒤
  실제로 **빨갛고 큰 점**이 찍히는 것은 육안으로 확인했다(스크린샷 `07_history.png`,
  회색·작은 예시 점 4개 대비). 다만 이건 시뮬레이터 화면 캡처로 본 것이지 실기 디스플레이의
  실제 색 표현(밝기·색온도 차이)까지 검증한 건 아니다. 코드상 `Canvas.drawCircle`에 어떤
  `Paint.color`가 전달되는지는 어떤 자동화 테스트도 검사하지 않는다는 점은 Task 7에서부터
  이미 알려진 공백이다.
- **웹 백업** — Task 9가 아직 완료되지 않아 URL 자체가 없다. §1-4에 채워 넣어야 할 빈칸이
  실물로 검증되기는커녕 아직 존재하지 않는다.
- **실물 밝기 환경에서의 글자 대비** — 시뮬레이터 스크린샷으로 색 대비(전경/배경 색상 차이)는
  확인했지만, 이는 화면 밝기와 무관한 값이다. 실제 전시장 조명·창가 직사광선 아래, 아이패드
  화면 밝기를 최대로 올린 상태에서 눈부심으로 인한 가독성 저하는 시뮬레이터로 재현이 안 되는
  영역이라 확인하지 못했다.
- **Apple 개발자 계정 / 실물 설치 자체** — 계정 준비 여부를 이 세션에서 확인할 방법이 없었다.
  브리프의 경고대로, **9/5까지 계정이 준비되지 않으면 네이티브 앱을 포기하고 웹 백업 단독으로
  전환할지 판단**해야 한다 — 이 결정은 사람 몫이다.
